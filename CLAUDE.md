Agent-facing rules for **Know Your Ward** — a static, no-build Bengaluru civic ward-information site. MapLibre GL JS for maps, vanilla ES modules (no framework, no bundler), data loaded client-side from local CSV/JSON files. There is no backend and no build step by design; the repo is deployed to Vercel (and is portable to any static host) exactly as committed. "Know Your Ward" is this project's engineering-facing name; the site's visitor-facing name (page `<title>`, meta description, eyebrow) is currently **"Nimma Ward, Nimma Vote."**

## Data & Keying Rules

- `W` (in `data-loader.js`) is keyed by **`uid`** (`{corporation}-{ward_id}`, e.g. `"West-25"`), never by `ward_name`. `ward_name` is incidentally unique in the current dataset but not structurally guaranteed across the 5 corporations.
- `nameIndex` maps a lowercased `ward_name` to its `uid`, for search/display only. Any new lookup/navigation code should resolve to `uid` and use `ward_name` only for rendering.
- CSV parsing uses PapaParse with `dynamicTyping: true`; blank cells become `null` (confirmed empirically), not `""` or `0` — don't add redundant empty-string guards to threshold logic that already checks `== null`.
- `neighbourhoods` and `old_wards` CSV columns are semicolon-joined free text and are parsed into arrays in `data-loader.js` (`parseNeighbourhoods`, `parseOldWards`) — don't re-split them elsewhere. `ward-view.js`'s head block renders these directly: `old_wards` (`[{name, pct}]`) under "Formed from old wards", `neighbourhoods` (`string[]`) under "Key areas" — both fall back to "Not available" when empty (`neighbourhoods` is blank for ~56 wards; `old_wards` is never blank in the current dataset).
- `public/data/ward_facts_questions.geojson` (369 features, one per ward) is the one deliberate exception to the uid-keying rule above: it's joined to `W` by **`ward_name`**, not `uid`, because that's the only shared key it carries. `data-loader.js` fetches it once (in the same `loadData()` `Promise.all` as every other source file), builds a `normalizeWardName`-keyed index (trim + collapse whitespace + lowercase, applied to both sides of the join — currently a 369/369 exact match), and attaches the matched feature's raw `properties` object to each ward as `ward.factsQuestions` (or `null` if unmatched, which only logs a `console.warn` when `isLocalDev()` — `location.hostname` is `localhost`/`127.0.0.1` — since there's no build-time env var in this project to gate on otherwise). This join runs once at load; ward navigation never re-fetches or re-matches. `ward.factsQuestions` holds the *entire* raw properties object (not a pre-picked subset), so a future field added to the GeoJSON needs no `data-loader.js` change — only a one-line addition to the field list in `ward-view.js` (see Facts Engine Rules below).
- `public/data/temperature.geojson` (369 features, one per ward) follows the identical join pattern, also by name rather than `uid` — keyed on the file's own `ward_name` property (as of its 2026 update; earlier vintages of this file used a bare `ward` property instead), resolved through the same `normalizeWardName`, still a 369/369 exact match. `buildTemperatureIndex`/the per-ward finalize loop in `data-loader.js` attach the matched feature's entire raw `properties` object as `ward.temperature` (or `null` if unmatched, same `isLocalDev()`-gated `console.warn`). `ward-view.js`'s Vulnerability hotspots row reads `lst_2026` (current land-surface temperature, °C) and `delta_lst` (change since 2015) off it; the file's earlier `blt_2025`/`delta_blt`/`ndvi_*`/`perm_*`/`uhi_*`/`water_2025` land-cover fields were dropped in the 2026 update and no longer exist — only `ward_name`, `lst_2015`, `lst_2026`, and `delta_lst` remain.
- `public/data/benchmarks_for_WID.csv` (11 rows: `Amenity`, `benchmark_text`, `benchmark`) is fetched once in the same `loadData()` `Promise.all` as every other source file and parsed with the same PapaParse convention as `wards.csv`. Unlike the two name-joined files above, this isn't a per-ward join — it's a small, ward-independent lookup table (`buildBenchmarkIndex`, keyed by normalized `Amenity` text) returned from `loadData()` as `benchmarks` and consumed only by `ward-view.js`'s Amenities grid (see Map Rules below). `normalizeWardName` is exported from `data-loader.js` and reused as-is for this join — despite its name it's a generic trim/collapse-whitespace/lowercase key normalizer, not ward-specific.

## Map Rules (`src/js/maps.js`)

- MapLibre GL JS only — this project does not use Leaflet.
- Basemap tiles are two stacked CARTO raster layers: `carto-base` (`dark_nolabels`, `tileUrl()`) sits at the bottom, and `carto-labels` (`dark_only_labels`, `labelTileUrl()`) — a transparent-background, text-only tile set — is layered on top so road/locality/area labels stay legible over the translucent ward-fill layers instead of being dimmed underneath them. This project has no light/dark theme toggle (removed in the 2026 redesign — see the note at the top of this file), so both maps always use the dark CARTO variant, matching the dark map cards throughout the design; `tileUrl()`/`labelTileUrl()` take no theme argument. `createMap` adds both at map creation; `raiseLabels(map)` re-raises `carto-labels` to the very top of the layer stack and is called once, after every other layer for that view has been added, in `home-view.js`'s and `ward-view.js`'s map `load` handlers (`ward-view.js` adds layers in several steps — boundary, neighbour outlines, amenity points, walk buffer — so this must run last, not from inside `addWardBoundaryLayer` itself). MapLibre does not support Leaflet's `{s}` subdomain placeholder — subdomains (`a`-`d`) must stay expanded into a literal array (both `tileUrl` and `labelTileUrl`).
- Both maps carry a floating "Reset Map" button (`addResetViewControl(map, defaultView)` in `maps.js`, reusing `.icon-btn`'s exact 44×44 circular styling and a copy of `ward-view.js`'s reset-arrows glyph sized to 18×18) — `aria-label="Reset Map"`, `title="Reset map view"`, absolutely positioned top-right inside the map's own container (`.map` carries `position: relative` for this; the button is appended directly via `map.getContainer().appendChild(...)`, no wrapper `<div>` needed) and wired to `map.easeTo({ center, zoom, bearing: 0, pitch: 0, duration: 600 })`. `addResetViewControl` is called once at the end of each map's `load` handler (after `raiseLabels`), with the "default view" it's given differing by map: the home choropleth's is the literal, known `{ center, zoom }` passed to `createMap` (no `fitBounds` involved there); the ward map's is captured by reading `getCenter()`/`getZoom()`/`getBearing()`/`getPitch()` immediately after its `fitBounds(bounds, { padding: 40, duration: 0 })` call, since that per-ward fit — not the `createMap` fallback params — is the map's real default view. On the ward map specifically, `#wardMap .map-reset-btn` carries an extra `top` offset so it sits just below `.wardmap-badge` (the "Showing: X (count)" pill, which already occupies that same top-right corner) rather than overlapping it; the home map has no such badge, so its button sits flush at the default inset.
- `LAYER` and `CORP_COLORS` are the single source of truth for every amenity icon/color and every corporation map fill color. Never hardcode a color for an amenity/corporation anywhere else.
- `LAYER[key].icon` is a hand-coded, `currentColor`-based inline-SVG string (one per amenity type) rendered in `ward-view.js`'s `.amrow` list — it is a visual pictogram only.
- The ward detail map uses `GBA_369_Wards_Enriched.geojson` for the ward boundary and renders real point markers for every entry in `POINT_SOURCES` (`data-loader.js`) — 14 source files covering polling booths, bus stops, metro stations, schools, anganwadis, parks, public toilets, lakes, two independent flood layers (`flood_prone`/`flood_vuln`), three independent police layers (`police`/`police_outpost`/`railway_police`), and fire stations. Every source file shares the same `ward_join_status`/`Point`-geometry schema produced by one spatial-join pipeline and is treated as final data — none of them are placeholders. `playground` and `pond` remain in `LAYER` with no backing source file, so their filter cards never render (matches today's behavior for any type with zero matched points); `park` (`public/data/Parks.geojson`) is a fully backed, walk-eligible (`LAYER.park.walk === true`) type like any other.
- Point features must be assigned by spatial point-in-ward checks against enriched ward boundaries, via `assignPointSource` (`data-loader.js`), run once per `POINT_SOURCES` key. Ignore `ward_join_status !== "matched"`, ignore non-Point/invalid geometries, and drop matched points that do not fall inside any enriched ward.
- `ward.polling` (the count shown on the Polling booths filter card) is authoritative from the enriched GeoJSON's `Num_Polling_Stations`, falling back to `wards.csv`'s `polling` column only when that's missing — never recompute it from the matched-marker array length, or a future edit to either source file can silently drift the displayed count away from the ground truth. This scalar-authoritative-count rule is polling-specific; the other 13 marker types (including `park`) have no equivalent enriched-geojson scalar to prefer for their *filter-card* count, so those counts are simply `layerPoints(...).length` — `park` does have an independent enriched-geojson scalar (`parks`/`parks_cov`, from `Park_Count`/`Park_Coverage_Percent`), but it's used only for `amenityRows`' coverage tuple element and citywide averages, never to override the filter-card/Amenities-row count. `data-loader.js`'s `spreadCoincidentPoints` nudges any exactly-coincident coordinates within a ward a few meters apart (many schools/stops host several co-located facilities) so every marker stays individually plottable — this now runs for every `POINT_SOURCES` key, not just polling, and keeps polling's marker-array length equal to `ward.polling` while ensuring markers don't stack invisibly on top of each other.
- `ward.pointMeta[key]` (data-loader.js) is a per-point metadata array (`{ name }`, or `{ name, num }` for polling) that is index-aligned with `ward.points[key]` — both arrays are pushed together inside `assignPointSource`, gated by a `POINT_NAME_FIELDS` lookup table, and `spreadCoincidentPoints` only mutates coordinate values in place (never reorders), so the alignment holds after spreading. Only `polling`, `school`, `metro`, and `flood_prone` are in `POINT_NAME_FIELDS` (and the matching `TYPES_WITH_META` allowlist in `maps.js`'s `layerPointMeta`) — every other source file's raw `Name` property is a uniform literal `"Placemark"` string with no real per-feature identity (confirmed empirically, not assumed), so those 9 types deliberately never get metadata pushed and hovering them shows no tooltip. `setActiveAmenityLayer`/`addAmenityPointsLayer` (maps.js) attach whatever metadata exists as each rendered point feature's `properties`, and the ward map's `amenity-points-circle` layer uses it to show a cursor-following `.map-tip` tooltip (`"<name>"`, or `"<name> · Booth <N>"` for polling) on hover.
- Ward Map filter cards render only for layers with valid point data in the selected ward. The Amenities grid (`amenityRows` in `maps.js`) now shares those same counts: each row's count is `layerPoints(uid, type, W).length`, the identical matched-marker count the corresponding Ward Map filter card shows — not a separate enriched-GeoJSON scalar. `amenityRows` still attaches the enriched-GeoJSON `*_cov` scalar as a 4th tuple element for `bus`/`metro`/`park`/`toilet`/`lake`, but `renderAmenities` (`ward-view.js`) no longer renders a coverage bar for any row — the Amenities grid shows only the icon, label, and count now (`.amrow`'s grid is 3 columns, `auto 1fr auto`). `amenityRows` has 13 rows: the original 12 amenity types, with the old merged `flood` row split into independent `flood_prone`/`flood_vuln` rows (matching the Ward Map's two independent flood filter cards) — `police_outpost` and `railway_police` remain map-filter-only, same as polling, and are still not Amenities rows. Because `playground` and `pond` have no backing point-source file (see `POINT_SOURCES` below), their Amenities rows now always read `0`, same as their permanently-absent Ward Map filter cards; `park` is backed by `Parks.geojson` and its row/card counts reflect real matched points. `renderAmenities()`/`renderVulnerability()` (`ward-view.js`) split those 13 `amenityRows` rows into two rendered grids — an 11-row Amenities grid and a 2-row "Vulnerability hotspots" grid (`flood_prone`/`flood_vuln` only) — both reusing identical `.sec`/`.amgrid`/`.amrow` markup and wired through the same page-wide `.amrow` click handler in `wireLayerClicks`, so `amenityRows()` itself is unchanged and still returns all 13 rows for each renderer to filter; this is a presentational split only, not a data-model change. `renderVulnerability()` additionally appends a third, non-interactive Temperature row (`renderTemperatureRow()`) as a **sibling of `.amgrid`**, not one of its rows — sourced from `ward.temperature` (see the `temperature.geojson` join above), reading `lst_2026`/`delta_lst`, formatted via the existing `fmt(value, 1)` helper as `Temperature: <lst_2026>°C (Increased by/Decreased by/No change <delta_lst>°C since 2015)` depending on the delta's sign. It deliberately uses a distinct class, `amrow-static` (never combined with the `amrow` token on the same element), rather than an `.amrow` modifier: `wireLayerClicks()`'s `document.querySelectorAll('.amrow')` wires every match into `layerPoints(uid, row.dataset.layer, W)`, which throws on an element with no `data-layer` (`LAYER[undefined].ptkey`) — so keeping this row outside that selector entirely, rather than adding an `if` guard, is what makes it structurally non-clickable and incapable of affecting the Ward Map, the flood rows' selected state, or the buffer-zone/walk-checkbox logic. It's also rendered outside `.amgrid` rather than as a third grid item, since `.amgrid` becomes a 3-column `auto-fit` CSS grid at the ≥900px breakpoint sized for short label+count content — the temperature sentence is long enough to wrap there and stretch the shared row-track around the shorter flood rows. Unlike every other data-dependent row on this page, the row itself is never omitted: when `ward.temperature` is `null` or `lst_2026`/`delta_lst` aren't finite numbers (still `isLocalDev()`-gated `console.warn`'d, now naming `lst_2026`), it renders `Temperature: N/A` instead of vanishing. Immediately after the temperature text — inside the same `.am-temp-text` span, so it flows with and wraps as part of the sentence rather than sitting in a separate column — a `.temp-info-link` anchor (`INFO_ICON`, a hand-coded info-circle SVG following the `TEMPERATURE_ICON`/`EXTERNAL_LINK_ICON` convention) links to `public/data/Temperature_2015_2026.pdf` with `target="_blank" rel="noopener"` (opens in a new tab, never auto-downloads) and a native `title`/`aria-label` reading "About this temperature data"; it renders unconditionally in both the real-data and N/A cases. `.temp-info-link` is a full 44×44px touch target (via padding, not negative margins) around a visually smaller 16px icon, matching this project's touch-target convention even though the control sits inline mid-sentence.
- Amenities-grid rows (not Vulnerability hotspots, not the Temperature row) also render a benchmark block sourced from `public/data/benchmarks_for_WID.csv` (see Data & Keying Rules above), joined by normalized `Amenity` text via `benchmarkFor()`/`renderBenchmarkBlock()` in `ward-view.js`. When the CSV's `benchmark` column has a positive numeric value (`Parks`/`Playgrounds`/`Schools`/`Anganwadis`: 5000, `Public toilets`: 400, `Police stations`: 90000, `Fire stations`: 50000), the row shows a compact progress bar toward `recommended = Math.ceil(w.pop / benchmark)` (clamped at 100%): `.am-benchmark-track` (a neutral gray tint, `color-mix(in srgb, var(--gray) 25%, var(--surface-2))` — not the brand's green-tinted `--inset`) plus `.am-benchmark-fill`, whose color is a performance tier driven by `progressTone(pct)` in `ward-view.js` — `--green` at/above 100% of recommended, `--light-green` for 75–99%, `--orange` for 40–74%, `--red` below 40% — via `.am-benchmark-fill--<tone>` modifier classes, alongside an `.am-benchmark-ratio` "`count` / `recommended` recommended" label. When `benchmark` is blank (`Bus stops`/`Metro stations`/`Lakes`/`Ponds / tanks`), the row shows a small `.am-benchmark-badge` instead — a static label keyed by `amenityRows()`'s `key` (not CSV text) in `BENCHMARK_BADGES`, colored by *category* rather than uniformly: `BADGE_TONES` in `ward-view.js` maps each known category label to a tone (`Network standard`→blue, `Accessibility based`→teal, `Coverage based`→indigo, `Geography based`→cyan, `Planning based`→gray, `Activity based`→orange, `Environmental`→green; unmatched falls back to gray), applied via `.am-benchmark-badge--<tone>` modifier classes using `tokens.css`'s `--blue`/`--teal`/`--indigo`/`--cyan`/`--gray`/`--orange`/`--green` custom properties. Only `blue` (Bus stops/Metro stations) and `cyan` (Lakes/Ponds) are reachable with today's CSV data; the rest exist for categories no current row uses yet, same "supported but currently unreachable" precedent the badge tone system already had once before. The badge shell itself is not the neutral `.pill` component, since `.pill`'s background is identical to `.amrow.is-clickable:hover`'s and would visually vanish on row hover. `benchmark_text` (the CSV's plain-language standard description) renders underneath as `.am-benchmark-desc` in both cases, whenever present. A row with no CSV match (none currently exist among the 11 Amenities rows) renders exactly as it did before this feature existed — `benchmarkFor()` returns `null` and contributes no markup. This is Amenities-section-only: `renderVulnerability()`'s flood rows and the Temperature row never call these helpers, and `amenityRows`/`LAYER`/`LAYER_ORDER` in `maps.js` (shared with the Ward Map filter cards) are untouched by it. `.am-benchmark-desc` is CSS-clamped to, and given an explicit `height: 2.9em` always reserving, exactly 2 lines — `-webkit-line-clamp: 2` still supplies the "…" ellipsis on genuinely long text, but the explicit height is what keeps a short 1-line description from collapsing its own box, which (combined with `.amgrid-benchmarks .amrow`'s own fixed `min-height` + `align-content: start`) is what keeps every Amenities row — badge or bar, 1-line or 2-line description — pixel-identical in height rather than only "close enough" (see the Styling & Theming/grid notes in Map Rules above for the original unevenness this replaced). `wireBenchmarkToggles()` (`ward-view.js`, called from `openWard()` after `document.fonts.ready` resolves, not immediately after render — measuring `scrollHeight`/`clientHeight` before the Manrope/PT Sans webfonts finish loading under-detects which descriptions actually overflow) adds a "Read more"/"Show less" toggle button only to descriptions that actually overflow their fixed box (`el.scrollHeight > el.clientHeight`), appending it as a *child* of `.am-benchmark-desc` (not a sibling) so `.am-benchmark-more`'s `position: absolute; right: 0; bottom: 0` lands it at the end of the visible second line rather than on a line of its own — expanding removes the fixed height via `.am-benchmark-desc--expanded` (`height: auto`, `overflow: visible`), no text-swapping, since the paragraph's full text is already in the DOM regardless of visual clipping. This button's click handler calls `e.stopPropagation()`, since it sits inside the same `.amrow` that `wireLayerClicks()` wires a click-to-switch-map-layer handler onto — without it, clicking "Read more" would also switch the Ward Map's active layer. A card's expanded state is the one exception to "every row is pixel-identical" — it can grow taller than its still-collapsed row-siblings until toggled back, a deliberate, accepted trade-off rather than something further solved.
- Keep the 800m walk checkbox visible, but apply buffers only to `LAYER[type].walk` layers. For non-walkable active layers such as polling, clear/disable the buffer behavior.
- Feature-state hover (`makeHoverTracker`) must always clear the previously-hovered feature id before setting a new one — a stuck highlight means this bookkeeping broke.
- The 800m walk buffer (`buildWalkBuffer`) uses a latitude-adjusted geodesic formula (`dLng = meters / (111320 * cos(lat))`) — Bengaluru sits at ~13°N, so a flat degree offset produces a visibly non-circular buffer. Don't simplify this back to a fixed offset.
- `wardAt`/`pointInWard` operate on GeoJSON `Polygon`/`MultiPolygon` geometry, including holes. Do not flatten a ward to `geometry.coordinates[0]`; wards such as `East-28` have multiple polygons and `North-21` has an interior ring.
- The ward map additionally plots a **secondary, dimmed marker layer** (`amenity-points-secondary` source, `amenity-points-secondary-circle` layer) for whichever amenity/vulnerability type is currently active: any point of that type belonging to a *different* ward, as long as it's within 1.6km of the current ward's boundary (a true buffer zone measured to the nearest edge of the ward polygon via `distanceMetersToWardBoundary`, not centroid distance — see `wardBbox`/`expandBbox`/`bboxesOverlap`/`pointToSegmentMeters`/`distanceMetersToWardBoundary` and the composing `nearbyExternalPoints`/`setExternalAmenityLayer` in `maps.js`). This is always on — it has no checkbox and is fully independent of `LAYER[type].walk`/the 800m walk-reach toggle, updating on every layer switch via one extra call inside `ward-view.js`'s `setLayer`, right alongside (but never gated by) `setWalkBufferLayer`. `wardBbox` lazily caches each ward's bounding box (ward geometry never changes in a session) so the expensive part — walking every boundary vertex — only happens once per ward per session; the actual "which other wards/points are nearby" set is still recomputed on every layer switch (cheap, bbox-prefiltered first) rather than cached, since it depends on `type`. The secondary layer is always inserted *below* `amenity-points-circle` (`map.addLayer(layer, 'amenity-points-circle')`, the same before-id trick `setWalkBufferLayer` already uses) so in-ward primary markers always visually win on any pixel overlap; its paint is identical to the primary layer's except `circle-opacity`/`circle-stroke-opacity: 0.45`, still using `LAYER[type].color` (never a new hardcoded hex). Hovering a named dimmed marker (same `TYPES_WITH_META` allowlist as primary markers) shows a `.map-tip` tooltip on desktop, exactly like the primary layer's — but the dimmed layer *also* gets a `click` handler (mirroring `home-view.js`'s hover-tip/click-popup pattern) that opens a small dismissible `.map-tip` popup on tap, so touch users get the same tooltip content without hover; only one such popup is open at a time (`activeSecondaryPopup` in `ward-view.js`), dismissed by tapping elsewhere on the map (default `closeOnClick`), tapping another marker, or `Escape` (a one-time `keydown` listener registered in `initWardView`, not `openWard`, to avoid leaking a new listener per ward navigation). Primary-marker hover wins over the dimmed layer on any exact pixel overlap via a `queryRenderedFeatures` check before showing the secondary hover tip.
- The ward map's dashed neighbor-ward outlines are driven entirely by the buffer-zone-qualifying set above, not a fixed nearest-N list — there is no independent "nearest wards" concept on this map anymore. `nearbyExternalPoints` (`maps.js`) also collects the distinct `otherUid`s that contributed at least one in-range point for the active type and returns them as `wardUids`; `setExternalAmenityLayer` passes this through, and `ward-view.js`'s `setLayer` immediately feeds it to `setBufferZoneWardsLayer` (`maps.js`), which builds a `buffer-zone-wards` source (via the existing `buildWardPolygonsGeoJSON({filterUids: wardUids})`) and two layers: `buffer-zone-wards-line` (the always-visible dashed outline, same `#93a29a`/`[2,2]` styling the old nearest-N outlines used) and `buffer-zone-wards-fill` (invisible at rest, `LAYER`-independent — reuses the ward-boundary green `#2f8f66` — feature-state-hover-driven to a mild `fill-opacity: 0.18` shadow, mirroring `addWardBoundaryLayer`'s existing hover-color pattern but opacity-only). Both layers recompute on every layer switch exactly like the dimmed markers themselves, so which neighboring wards get an outline changes with the active type, and a type with zero nearby external points shows zero outlines. Hovering a qualifying ward's area (desktop) shows the green shadow plus a `.map-tip` tooltip in the format `Ward <ward_id> · <name>` (no corporation, unlike the home page's equivalent tooltip); clicking/tapping it opens a `.ward-popup` (the exact same component `home-view.js`'s choropleth ward-click popup uses) with `Ward: <name>` and a **"View this ward"** button — only pressing that button navigates (via the same `onOpenWard` callback), so clicking elsewhere on a qualifying ward's area does not by itself leave the current ward. This CTA is ward-area-only: a `queryRenderedFeatures` check against `amenity-points-secondary-circle` makes an individual dimmed marker's own tooltip win whenever the two would otherwise overlap, so the ward-level tooltip/shadow/CTA never fires on top of a marker.
- **Important distinction**: `buffer-zone-wards-fill`/`-line` render the qualifying ward's *entire, unclipped* polygon (`wardGeometry(W[uid])`, the same full shape used everywhere else) — a ward can easily span several km, while only a small sliver of it may actually sit within 1.6km of the current ward's boundary (e.g. `Byrathi`/`East-28` relative to `K Narayanapura`/`East-1`: genuinely adjacent and correctly qualifying via real bus stops a few meters from their shared border, yet Byrathi's own polygon extends up to ~4.75km away at its far corner). True polygon clipping was deliberately not implemented (it would need a geometry/buffering library this project avoids). Instead, the `mousemove`/`click` handlers on `buffer-zone-wards-fill` in `ward-view.js` each additionally call `distanceMetersToWardBoundary(e.lngLat.lng, e.lngLat.lat, uid, W)` and bail out (no shadow, no tooltip, no popup) whenever that specific cursor/tap position is more than 1.6km from the current ward's boundary — so the rendered/dashed-outlined shape can be large, but the shadow/tooltip/CTA only ever activate for the part of it genuinely within the buffer zone. This reuses the exact same distance function and 1600m threshold as the point-qualification logic above, so the two can't disagree, and is cheap enough to run on every `mousemove` (~0.02ms/call even against a 500+-vertex boundary). `activeNeighborWardPopup`/`closeNeighborWardPopup` in `ward-view.js` track/dismiss this popup the same way `activeSecondaryPopup` does for marker popups, both reset per `openWard()` call and both closable via the same one-time `Escape` listener in `initWardView`. `nearbyWards`/`centroid`/`forEachWardOuterCoordinate` (the old nearest-N-by-centroid helpers) were removed from `maps.js` as dead code once nothing called them anymore.

## Voter FAQ View Rules (`src/js/voter-faq-view.js`)

- Every question and answer in `CATEGORIES` is copied verbatim from the source Voter FAQs document — including its own wording quirks (e.g. "Specific Intensive Revision", "erstwhile"). Do not reword, shorten, or "correct" any question/answer text; only the 8-category grouping and markup structure are this project's own design, not the source content. (`--faq-nav-clearance` is a runtime-set variable like `--ripple-x`/`--ripple-y` — expected to be absent from `tokens.css`'s static definitions, not a gap in token coverage.)

Deliberately **do not** force an `updateActiveCategory()` recompute when suppression is released — a short section (e.g. "Key dates", one item) can land its scroll position close enough to the next section that the 40%-band geometry would immediately "correct" the just-clicked category to its neighbor, visibly fighting the user's own click. The clicked category stays active until the user's own further scrolling naturally moves it on.
- `updateActiveCategory()` itself is still computed directly via `getBoundingClientRect()` on every section rather than trusting `IntersectionObserver` entries' `isIntersecting` flags — near the very top or bottom of the page, no category falls inside the observer's shrunk `rootMargin` band, so `isIntersecting` never fires `true` for anything there, and naively leaving the last-highlighted category active would show a stale highlight after scrolling back to the top. The observer is used only as an efficient "something changed, recompute" trigger; the answer itself is always the last category whose top has scrolled above the 40%-viewport-height band line, falling back to the first category before that's ever true.
- There is no floating "Voter FAQs" button anymore (`#voterFaqFab` was removed in the 2026 redesign) — "Voter FAQs" is a normal link in the persistent site header's nav (`header.js`), active-highlighted like `Home`/`Methodology` via `setHeaderState`.

The overrides tighten `.category`'s margin/padding (32px → 16px) and its `h3`-to-first-item gap (12px → 8px), and shrink the gap below the hero's CTA buttons (`.cover` bottom padding 48px → 24px, `.callout` top margin 16px → 12px) — all as flat values that apply at every width, since an ID-scoped selector outranks `.sec`'s `@media (min-width:900px)` padding bump regardless of source order. Do not "fix" this by editing the shared `.sec`/`.cover`/`.callout` rules directly.
- **Instant search** (`#faqSearchInput`, sitting between `.callout` and `.faq-section`, debounced ~200ms via a local `debounce()` copied from `home-view.js`'s own pattern) filters live against a `searchIndex` built once at init from `CATEGORIES` — each `.accordion-item` carries a `data-item-index` (added by `renderCategory`) so a DOM node can be resolved back to its exact source `{q, a}` via `closest('.category').id` + that index, rather than relying on iteration-order coupling between two separate DOM passes. Matching is plain case-insensitive substring against the question text plus a `stripHtml(item.a)`-flattened copy of the answer (which naturally covers `<li>` bullets too) — no fuzzy/stemming logic, confirmed sufficient for every example in the original request ("corporator", "Form 6" — answer-only, not in the question text — and "SIR").
- Highlighting (`highlightIn`, reusing the site's one existing `mark` style — no new highlight class) walks `NodeFilter.SHOW_TEXT` nodes via `TreeWalker` and splices `<mark>` elements in as real DOM nodes, never via string concatenation — this is what keeps an answer's `<a href>`/`<strong>`/nested `<ul><li>` markup intact under highlighting and is not an XSS risk despite wrapping user-typed query text. Every keystroke resets `triggerSpan.textContent`/`panelInner.innerHTML` back to the pristine `item.q`/`item.a` before reapplying highlights — this (not a separate "strip old marks" step) is what keeps re-highlighting and clearing drift-free.
- While a search is active: non-matching `.accordion-item`s and `.category` sections (a whole section only if *none* of its items match) are hidden via the native `hidden` attribute; matching items are force-expanded through the exact same fields (`data-open`, `aria-expanded`, `panel.style.maxHeight`) the manual accordion click handler already uses, so the existing CSS transition/chevron-rotate needs no changes; and `.cat-nav` is hidden too, per "filtering makes category navigation unnecessary." `.cat-nav` has its own `display:flex` rule, which beats the native `[hidden]` UA style on specificity grounds (any author rule outranks a UA rule) — same gotcha `base.css`'s `.voter-faq-fab[hidden] { display:none }` already works around, solved here with an identical `.cat-nav[hidden] { display:none }` override in `components.css`. `.category`/`.accordion-item` have no explicit `display` set, so plain `hidden` works on them unmodified.
- Clearing search (the inline × button, `Escape`, or an empty-state suggestion/`Clear Search` action) always runs through the same `applySearch('')` / `clearSearch()` path as typing — there is no separate "restore" code path to keep in sync. `#faqSearchSummary` (`aria-live="polite"`, "N results found"/"1 result found") and `#faqEmptyState` (shown only when a query is active and zero items match, with clickable `.pill.faq-empty-chip` suggestions reusing the existing pill component) are both driven by the same function.

- **Ward-name autosuggestion**: unchanged by the 2026 redesign except for its container's restyling. `#findSearch` is wrapped in `.find-search-wrap` (`position: relative`, home-view.js), which also holds `#wardSuggest` (`.ward-suggest`), a floating dropdown hidden by default. The dropdown merges two sources, capped at 6 rows total (`SUGGEST_CAP`): (1) `computeLocalMatches()` — an instant, ungated, no-network substring match of the typed text against `ward_name` only, re-run synchronously on every keystroke starting from the first character, ranking wards whose name *starts with* the query above ones that merely contain it (alphabetical within each group) — this is what makes the dropdown appear immediately rather than waiting on a network round trip; and (2) `resolveLandmarkMatches()` — a still-debounced (400ms, `home-view.js`'s `debounce()`, 3-character minimum, since it's a real third-party network call) query against the public OSM Nominatim API (`https://nominatim.openstreetmap.org/search`, hardcoded `country=india`, `city=bangalore`, `format=jsonv2`, `limit=5`, `email=sss@gmail.com` — Nominatim's usage-policy-accepted identification method, since browsers won't let script set a custom `User-Agent` header — and the typed text as the dynamic `amenity` param) for resolving a typed **landmark** (a bus stop, locality, or other place that isn't itself a ward name) to the ward it physically sits in. Each Nominatim result is checked two ways before being shown: `findWardNameTextMatch()` fuzzy-matches (case-insensitive substring, checked in both directions, longest-`ward_name`-wins on a tie) the result's combined `name` + `display_name` text against every local `ward_name`; if that finds a candidate ward, the result's `lat`/`lon` is run through `wardAt()` (`maps.js`, the same point-in-polygon helper "Use my location" uses) and **must** resolve to that same candidate ward or the result is dropped entirely — a text match that geometry doesn't confirm (a coincidental name mention that isn't actually where the point is) is never shown, on either ward. When no ward name appears in the result's text at all, the point-in-polygon result is used directly with no text gate, unchanged from a plain "whichever ward contains this point" lookup — e.g. a landmark like "Vidhana Soudha" (no textual relation to any ward name) still resolves to and displays whatever ward its coordinates fall inside. A resolved ward is merged into the dropdown with a "near `<landmark>`" subtext (in place of the usual "Ward N · Corporation" line) filling any of the 6 rows the local match didn't already take, deduped by `uid`. A prior in-flight Nominatim request is aborted via a module-level `AbortController` before each new one fires, and a module-level `suggestRequestSeq` counter additionally guards every async landmark result against being applied after a newer keystroke has already superseded it (covers cases `AbortController` alone can't, e.g. the query dropping back below the 3-character minimum before an in-flight fetch settles). Clicking a row navigates via the same `onOpenWard(uid)` callback the main ward list uses. The dropdown also closes on `Escape` and on any click outside `.find-search-wrap`. `data-loader.js`'s `nameIndex` is not used by any of this — it remains computed but unconsumed outside `data-loader.js`, as it was originally.
