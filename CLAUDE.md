# CLAUDE.md

Agent-facing rules for **Know Your Ward** — a static, no-build Bengaluru civic ward-information site. MapLibre GL JS for maps, vanilla ES modules (no framework, no bundler), data loaded client-side from local CSV/JSON files. There is no backend and no build step by design; the repo is deployed to Vercel (and is portable to any static host) exactly as committed. "Know Your Ward" is this project's engineering-facing name; the site's visitor-facing name (page `<title>`, meta description, eyebrow) is currently **"Nimma Ward, Nimma Vote."**

## Data & Keying Rules

- `W` (in `data-loader.js`) is keyed by **`uid`** (`{corporation}-{ward_id}`, e.g. `"West-25"`), never by `ward_name`. `ward_name` is incidentally unique in the current dataset but not structurally guaranteed across the 5 corporations.
- `nameIndex` maps a lowercased `ward_name` to its `uid`, for search/display only. Any new lookup/navigation code should resolve to `uid` and use `ward_name` only for rendering.
- CSV parsing uses PapaParse with `dynamicTyping: true`; blank cells become `null` (confirmed empirically), not `""` or `0` — don't add redundant empty-string guards to threshold logic that already checks `== null`.
- `neighbourhoods` and `old_wards` CSV columns are semicolon-joined free text and are parsed into arrays in `data-loader.js` (`parseNeighbourhoods`, `parseOldWards`) — don't re-split them elsewhere. `ward-view.js`'s head block renders these directly: `old_wards` (`[{name, pct}]`) under "Formed from old wards", `neighbourhoods` (`string[]`) under "Key areas" — both fall back to "Not available" when empty (`neighbourhoods` is blank for ~56 wards; `old_wards` is never blank in the current dataset).
- `public/data/ward_facts_questions.geojson` (369 features, one per ward) is the one deliberate exception to the uid-keying rule above: it's joined to `W` by **`ward_name`**, not `uid`, because that's the only shared key it carries. `data-loader.js` fetches it once (in the same `loadData()` `Promise.all` as every other source file), builds a `normalizeWardName`-keyed index (trim + collapse whitespace + lowercase, applied to both sides of the join — currently a 369/369 exact match), and attaches the matched feature's raw `properties` object to each ward as `ward.factsQuestions` (or `null` if unmatched, which only logs a `console.warn` when `isLocalDev()` — `location.hostname` is `localhost`/`127.0.0.1` — since there's no build-time env var in this project to gate on otherwise). This join runs once at load; ward navigation never re-fetches or re-matches. `ward.factsQuestions` holds the *entire* raw properties object (not a pre-picked subset), so a future field added to the GeoJSON needs no `data-loader.js` change — only a one-line addition to the field list in `ward-view.js` (see Facts Engine Rules below).

## Map Rules (`src/js/maps.js`)

- MapLibre GL JS only — this project does not use Leaflet.
- Basemap tiles are two stacked CARTO raster layers, both theme-swapped together: `carto-base` (`light_nolabels`/`dark_nolabels`, `tileUrlForTheme`) sits at the bottom, and `carto-labels` (`light_only_labels`/`dark_only_labels`, `labelTileUrlForTheme`) — a transparent-background, text-only tile set — is layered on top so road/locality/area labels stay legible over the translucent ward-fill layers instead of being dimmed underneath them. `createMap` adds both at map creation; `raiseLabels(map)` re-raises `carto-labels` to the very top of the layer stack and is called once, after every other layer for that view has been added, in `home-view.js`'s and `ward-view.js`'s map `load` handlers (`ward-view.js` adds layers in several steps — boundary, neighbour outlines, amenity points, walk buffer — so this must run last, not from inside `addWardBoundaryLayer` itself). MapLibre does not support Leaflet's `{s}` subdomain placeholder — subdomains (`a`-`d`) must stay expanded into a literal array (both `tileUrlForTheme` and `labelTileUrlForTheme`).
- `LAYER` and `CORP_COLORS` are the single source of truth for every amenity icon/color and every corporation map fill color. Never hardcode a color for an amenity/corporation anywhere else.
- `LAYER[key].icon` is a hand-coded, `currentColor`-based inline-SVG string (one per amenity type) rendered in `ward-view.js`'s `.amrow` list — it is a visual pictogram only.
- The ward detail map uses `GBA_369_Wards_Enriched.geojson` for the ward boundary and renders real point markers for every entry in `POINT_SOURCES` (`data-loader.js`) — 14 source files covering polling booths, bus stops, metro stations, schools, anganwadis, parks, public toilets, lakes, two independent flood layers (`flood_prone`/`flood_vuln`), three independent police layers (`police`/`police_outpost`/`railway_police`), and fire stations. Every source file shares the same `ward_join_status`/`Point`-geometry schema produced by one spatial-join pipeline and is treated as final data — none of them are placeholders. `playground` and `pond` remain in `LAYER` with no backing source file, so their filter cards never render (matches today's behavior for any type with zero matched points); `park` (`public/data/Parks.geojson`) is a fully backed, walk-eligible (`LAYER.park.walk === true`) type like any other.
- Point features must be assigned by spatial point-in-ward checks against enriched ward boundaries, via `assignPointSource` (`data-loader.js`), run once per `POINT_SOURCES` key. Ignore `ward_join_status !== "matched"`, ignore non-Point/invalid geometries, and drop matched points that do not fall inside any enriched ward.
- `ward.polling` (the count shown on the Polling booths filter card) is authoritative from the enriched GeoJSON's `Num_Polling_Stations`, falling back to `wards.csv`'s `polling` column only when that's missing — never recompute it from the matched-marker array length, or a future edit to either source file can silently drift the displayed count away from the ground truth. This scalar-authoritative-count rule is polling-specific; the other 13 marker types (including `park`) have no equivalent enriched-geojson scalar to prefer for their *filter-card* count, so those counts are simply `layerPoints(...).length` — `park` does have an independent enriched-geojson scalar (`parks`/`parks_cov`, from `Park_Count`/`Park_Coverage_Percent`), but it's used only for `amenityRows`' coverage tuple element and citywide averages, never to override the filter-card/Amenities-row count. `data-loader.js`'s `spreadCoincidentPoints` nudges any exactly-coincident coordinates within a ward a few meters apart (many schools/stops host several co-located facilities) so every marker stays individually plottable — this now runs for every `POINT_SOURCES` key, not just polling, and keeps polling's marker-array length equal to `ward.polling` while ensuring markers don't stack invisibly on top of each other.
- `ward.pointMeta[key]` (data-loader.js) is a per-point metadata array (`{ name }`, or `{ name, num }` for polling) that is index-aligned with `ward.points[key]` — both arrays are pushed together inside `assignPointSource`, gated by a `POINT_NAME_FIELDS` lookup table, and `spreadCoincidentPoints` only mutates coordinate values in place (never reorders), so the alignment holds after spreading. Only `polling`, `school`, `metro`, and `flood_prone` are in `POINT_NAME_FIELDS` (and the matching `TYPES_WITH_META` allowlist in `maps.js`'s `layerPointMeta`) — every other source file's raw `Name` property is a uniform literal `"Placemark"` string with no real per-feature identity (confirmed empirically, not assumed), so those 9 types deliberately never get metadata pushed and hovering them shows no tooltip. `setActiveAmenityLayer`/`addAmenityPointsLayer` (maps.js) attach whatever metadata exists as each rendered point feature's `properties`, and the ward map's `amenity-points-circle` layer uses it to show a cursor-following `.map-tip` tooltip (`"<name>"`, or `"<name> · Booth <N>"` for polling) on hover.
- Ward Map filter cards render only for layers with valid point data in the selected ward. The Amenities grid (`amenityRows` in `maps.js`) now shares those same counts: each row's count is `layerPoints(uid, type, W).length`, the identical matched-marker count the corresponding Ward Map filter card shows — not a separate enriched-GeoJSON scalar. `amenityRows` still attaches the enriched-GeoJSON `*_cov` scalar as a 4th tuple element for `bus`/`metro`/`park`/`toilet`/`lake`, but `renderAmenities` (`ward-view.js`) no longer renders a coverage bar for any row — the Amenities grid shows only the icon, label, and count now (`.amrow`'s grid is 3 columns, `auto 1fr auto`). `amenityRows` has 13 rows: the original 12 amenity types, with the old merged `flood` row split into independent `flood_prone`/`flood_vuln` rows (matching the Ward Map's two independent flood filter cards) — `police_outpost` and `railway_police` remain map-filter-only, same as polling, and are still not Amenities rows. Because `playground` and `pond` have no backing point-source file (see `POINT_SOURCES` below), their Amenities rows now always read `0`, same as their permanently-absent Ward Map filter cards; `park` is backed by `Parks.geojson` and its row/card counts reflect real matched points. `renderAmenities()`/`renderVulnerability()` (`ward-view.js`) split those 13 `amenityRows` rows into two rendered grids — an 11-row Amenities grid and a 2-row "Vulnerability hotspots" grid (`flood_prone`/`flood_vuln` only) — both reusing identical `.sec`/`.amgrid`/`.amrow` markup and wired through the same page-wide `.amrow` click handler in `wireLayerClicks`, so `amenityRows()` itself is unchanged and still returns all 13 rows for each renderer to filter; this is a presentational split only, not a data-model change.
- Keep the 800m walk checkbox visible, but apply buffers only to `LAYER[type].walk` layers. For non-walkable active layers such as polling, clear/disable the buffer behavior.
- Feature-state hover (`makeHoverTracker`) must always clear the previously-hovered feature id before setting a new one — a stuck highlight means this bookkeeping broke.
- The 800m walk buffer (`buildWalkBuffer`) uses a latitude-adjusted geodesic formula (`dLng = meters / (111320 * cos(lat))`) — Bengaluru sits at ~13°N, so a flat degree offset produces a visibly non-circular buffer. Don't simplify this back to a fixed offset.
- `wardAt`/`pointInWard` operate on GeoJSON `Polygon`/`MultiPolygon` geometry, including holes. Do not flatten a ward to `geometry.coordinates[0]`; wards such as `East-28` have multiple polygons and `North-21` has an interior ring.

## Facts Engine Rules (`src/js/ward-view.js`)

- `buildFacts(w)` and `suggestedQuestions(w)` no longer compute anything — they read pre-written, ward-specific text straight off `w.factsQuestions` (see Data & Keying Rules below), picking a fixed, ordered field list (`DID_YOU_KNOW_FIELDS` = `did_you_know_1..3`, `CANDIDATE_QUESTION_FIELDS` = `question_1..5`) and dropping any null/empty/missing value via a shared `isBlank`/`orderedFields` helper. There is no threshold logic, tone (`warn`/`bad`), or category label left in this engine — content and severity framing both live in the source data file now, not in this file. The field lists themselves are the output cap (3 facts, 5 questions max) — do not reintroduce a `.slice()` cap, there's nothing left to cap beyond the field list length.
- `renderFacts`/`renderAsk` `esc()`-escape every fact/question string before rendering (this data is external file content now, not HTML this module builds itself) into the same `.factslist`/`.fact` and `.qlist`/`<li>` markup as before — `.fact` cards render plain text with no tone class and no `.k` category eyebrow (the old cards had both; the new source provides neither signal).
- Flood-prone spot counts come from enriched GeoJSON `FloodProne_Count` and are exposed to the view as the ward-level scalar `ward.flood_prone`; `ward.flood_vuln` is currently `0` in the normalized app data. These are separate, independently-sourced values from the Ward Map's `flood_prone`/`flood_vuln` marker layers (`ward.points.flood_prone`/`ward.points.flood_vuln`, spatially matched from `Flood_Prone_Locations_Map.geojson`/`Map_of_Locations_Vulnerable_to_Flooding_in.geojson`) — same names, different data paths (ward-level enriched scalar vs. individually plotted points), so don't assume they'll always agree in count.

## Styling & Theming Rules

- All brand colors, spacing, and elevation values live only in `src/styles/tokens.css` as named custom properties (Open City brand palette: green primary, red alert, yellow highlight, a 4pt spacing scale `--space-1`..`--space-7`, and a 3-step elevation scale `--shadow-1`/`--shadow-2`/`--shadow-3`). Components consume tokens (`var(--...)`) — never hardcode a brand hex value in `components.css` or in JS-rendered markup.
- `:root` (light) and `[data-theme="dark"]` in `tokens.css` must always be updated together — this project has no separate "light-only" or "dark-only" component file.
- `LAYER`/`CORP_COLORS` hexes in `maps.js` are intentionally theme-agnostic (chosen to read on both the light and dark CARTO basemaps) — don't add a per-theme marker color override unless a real contrast problem is found during manual verification.
- Fonts: Manrope (`--font-display`/`--font-stat`, headings and stat numbers) and PT Sans (`--font-body`, body text) — do not reintroduce Poppins, Inter, Inter Tight, Playfair Display, or Plus Jakarta Sans. Manrope is the deliberate substitute for the brand guideline's Aileron, which is not on Google Fonts — don't "fix" it in either direction.
- `--lime` (`#c8e537`, the Open City accent) is dark-background-only — it is near-invisible on white (~1.4:1 contrast). It appears in exactly two places, both scoped under `[data-theme="dark"]`: the home search input's `:focus-visible` ring and the eyebrow dot. Do not use it in the light theme, for text, or as a general highlight.
- Touch targets on interactive elements (`.btn`, `.ward-row`, `.icon-btn`) are `min-height: 44px` — preserve this on any further edits.
- Text color follows a 3-tier hierarchy: body/description-length copy uses `--ink` (full contrast — e.g. `.panel p`, `.ward-def`, `.cand-intro`), inline metadata uses `--muted` (e.g. `.ward-row-meta`, `.whead-meta`, `.candparty`), and uppercase captions/labels use `--hint` (e.g. `.fact .k`, `.map-caption`, `.find-count`, `.whead-origin-block .label`). Don't put sentence-length text on `--muted`/`--hint` — those tones are for short secondary labels, not paragraphs.

## Voter FAQ View Rules (`src/js/voter-faq-view.js`)

- Every question and answer in `CATEGORIES` is copied verbatim from the source Voter FAQs document — including its own wording quirks (e.g. "Specific Intensive Revision", "erstwhile"). Do not reword, shorten, or "correct" any question/answer text; only the 8-category grouping and markup structure are this project's own design, not the source content.
- `.cat-nav` uses the exact *same* layout at every viewport width, with no per-breakpoint override at all — a full-width bar sitting above the category cards (not beside them), `position: sticky; top: env(safe-area-inset-top)` (flush against the true top — a nonzero offset here previously left a gap where content visibly scrolled up through it above the docked bar) and always `flex-wrap: nowrap; overflow-x: auto` (horizontal chip-scroll, never wraps onto extra rows, on desktop too). Do not add a per-breakpoint override back — not a `210px 1fr` sidebar grid, not a `flex-wrap: wrap` desktop variant; both were tried and explicitly reverted. Docking flush needs no separate clearance from `.topcluster`'s fixed theme-toggle button: the nav lives inside `#voterFaqContainer.container`, whose own right padding already keeps all content well clear of the toggle at every width (see the `.container` padding `clamp()` in `base.css`) — the toggle floats in the body-background margin outside the nav's own box, never over it.
- Because the nav's height is otherwise still measured rather than hardcoded (defensive against font-loading/content shifts, not because it varies by breakpoint anymore), `.category { scroll-margin-top }` is set dynamically: `initVoterFaqView` observes `.cat-nav` with a `ResizeObserver` and writes `topOffset + navHeight + 12px` to a `--faq-nav-clearance` custom property (on `#voterFaqContainer`, inherited by every `.category`). (`--faq-nav-clearance` is a runtime-set variable like `--ripple-x`/`--ripple-y` — expected to be absent from `tokens.css`'s static definitions, not a gap in token coverage.)
- The active-category highlight is centralized in one `setActive(id)` helper (both the click handler and the scroll-spy call it, never toggling `.active` classes directly) so a category becomes visibly active *immediately* on click rather than waiting for the scroll animation to catch up, and so the active chip is always auto-centered in the nav's horizontal scroll (`scrollIntoView({inline:'center', block:'nearest'})` — scoped to `.cat-nav` itself, since `overflow-x:auto` makes its paired `overflow-y` compute to `auto` too per the CSS overflow spec, making it its own nearest scrolling ancestor on both axes and unable to leak into scrolling the page).
- Clicking a nav button sets `suppressScrollSpy = true` so the sections it smooth-scrolls past on the way to the target don't flicker active, released via a `scrollend` listener (with a 1s `setTimeout` fallback for browsers without it). Deliberately **do not** force an `updateActiveCategory()` recompute when suppression is released — a short section (e.g. "Key dates", one item) can land its scroll position close enough to the next section that the 40%-band geometry would immediately "correct" the just-clicked category to its neighbor, visibly fighting the user's own click. The clicked category stays active until the user's own further scrolling naturally moves it on.
- `updateActiveCategory()` itself is still computed directly via `getBoundingClientRect()` on every section rather than trusting `IntersectionObserver` entries' `isIntersecting` flags — near the very top or bottom of the page, no category falls inside the observer's shrunk `rootMargin` band, so `isIntersecting` never fires `true` for anything there, and naively leaving the last-highlighted category active would show a stale highlight after scrolling back to the top. The observer is used only as an efficient "something changed, recompute" trigger; the answer itself is always the last category whose top has scrolled above the 40%-viewport-height band line, falling back to the first category before that's ever true.
- `#voterFaqFab` is styled as the site's primary CTA (reusing `.btn-primary`'s exact green/white token pairing, a `100px` pill radius, and this codebase's `color-mix()` convention — already used for the dark-theme search-input focus ring — for its idle pulse glow) rather than a neutral chrome element like `.topcluster`. Its `bottom`/`right` offsets use `clamp(18px, 4vw, 28px)` (matching `.container`'s own `clamp()` padding convention) rather than a flat value, and it fades out (opacity/pointer-events, not `hidden`) whenever `#siteFooter` scrolls into view — a dedicated `IntersectionObserver` set up once in `main.js`'s `boot()`, independent of the page-level `fab.hidden = name === 'voter-faq'` toggle in `showView()` — so the fixed-position button never sits on top of footer content once a user scrolls to the bottom of any page.
- The `.category` cards, the hero's `.cover`, and the `.callout` key-dates box all use `#voterFaqContainer`-scoped density overrides (`components.css`, immediately after `.rule-chip`) rather than editing `.sec`/`.cover`/`.callout` themselves — those three classes are shared with the ward-detail and methodology views (and `.cover` with the home hero), so a direct edit would have changed those pages too. The overrides tighten `.category`'s margin/padding (32px → 16px) and its `h3`-to-first-item gap (12px → 8px), and shrink the gap below the hero's CTA buttons (`.cover` bottom padding 48px → 24px, `.callout` top margin 16px → 12px) — all as flat values that apply at every width, since an ID-scoped selector outranks `.sec`'s `@media (min-width:900px)` padding bump regardless of source order. Do not "fix" this by editing the shared `.sec`/`.cover`/`.callout` rules directly.
- **Instant search** (`#faqSearchInput`, sitting between `.callout` and `.faq-section`, debounced ~200ms via a local `debounce()` copied from `home-view.js`'s own pattern) filters live against a `searchIndex` built once at init from `CATEGORIES` — each `.accordion-item` carries a `data-item-index` (added by `renderCategory`) so a DOM node can be resolved back to its exact source `{q, a}` via `closest('.category').id` + that index, rather than relying on iteration-order coupling between two separate DOM passes. Matching is plain case-insensitive substring against the question text plus a `stripHtml(item.a)`-flattened copy of the answer (which naturally covers `<li>` bullets too) — no fuzzy/stemming logic, confirmed sufficient for every example in the original request ("corporator", "Form 6" — answer-only, not in the question text — and "SIR").
- Highlighting (`highlightIn`, reusing the site's one existing `mark` style — no new highlight class) walks `NodeFilter.SHOW_TEXT` nodes via `TreeWalker` and splices `<mark>` elements in as real DOM nodes, never via string concatenation — this is what keeps an answer's `<a href>`/`<strong>`/nested `<ul><li>` markup intact under highlighting and is not an XSS risk despite wrapping user-typed query text. Every keystroke resets `triggerSpan.textContent`/`panelInner.innerHTML` back to the pristine `item.q`/`item.a` before reapplying highlights — this (not a separate "strip old marks" step) is what keeps re-highlighting and clearing drift-free.
- While a search is active: non-matching `.accordion-item`s and `.category` sections (a whole section only if *none* of its items match) are hidden via the native `hidden` attribute; matching items are force-expanded through the exact same fields (`data-open`, `aria-expanded`, `panel.style.maxHeight`) the manual accordion click handler already uses, so the existing CSS transition/chevron-rotate needs no changes; and `.cat-nav` is hidden too, per "filtering makes category navigation unnecessary." `.cat-nav` has its own `display:flex` rule, which beats the native `[hidden]` UA style on specificity grounds (any author rule outranks a UA rule) — same gotcha `base.css`'s `.voter-faq-fab[hidden] { display:none }` already works around, solved here with an identical `.cat-nav[hidden] { display:none }` override in `components.css`. `.category`/`.accordion-item` have no explicit `display` set, so plain `hidden` works on them unmodified.
- Clearing search (the inline × button, `Escape`, or an empty-state suggestion/`Clear Search` action) always runs through the same `applySearch('')` / `clearSearch()` path as typing — there is no separate "restore" code path to keep in sync. `#faqSearchSummary` (`aria-live="polite"`, "N results found"/"1 result found") and `#faqEmptyState` (shown only when a query is active and zero items match, with clickable `.pill.faq-empty-chip` suggestions reusing the existing pill component) are both driven by the same function.

## Verification Rules

This project has no bundler, linter, formatter, or type checker — that is a deliberate architectural choice (zero-build static site), not an oversight. Do not add `package.json`/ESLint/Prettier/TypeScript without discussing it first. The real static gates for any change here are:

1. `node --input-type=module --check < path/to/file.js` for every changed file in `src/js/` — the only syntax gate available for ES modules with no bundler.
2. A `grep` sweep confirming: no banned terms reappear (`chart.js`, `plus jakarta`), no leftover reference to a removed color/token, and every ID/class in the "must-preserve selectors" list above is still present in `src/js/*.js`.
3. Confirm every `var(--...)` used in `base.css`/`components.css`/`transition.css` has a matching definition in `tokens.css` (`:root` or `[data-theme="dark"]`) — except `--ripple-x`/`--ripple-y`, which are set at runtime by `theme.js`, not defined statically.

UI/CSS changes additionally require a manual browser walk of all 4 views (home, ward, methodology, voter FAQs), in both themes, at a few widths — there is no automated screenshot or test-runner tooling in this repo. See `.claude/skills/verify-and-update-docs/SKILL.md` for the full workflow.

## Do Not

- Do not add Chart.js, Leaflet, Plus Jakarta Sans, Inter, Inter Tight, Playfair Display, or Poppins back into the project (Poppins was intentionally replaced by Manrope, the closest Google-Fonts match to the brand's Aileron).
- Do not add a bundler, package.json, or any npm dependency without discussing it first — the zero-build static-site architecture is intentional.
- Do not key ward data by `ward_name` — always `uid`.

- **Ward-name autosuggestion**: `#findSearch` is wrapped in `.find-search-wrap` (`position: relative`, home-view.js), which also holds `#wardSuggest` (`.ward-suggest`), a floating dropdown hidden by default. The dropdown merges two sources, capped at 6 rows total (`SUGGEST_CAP`): (1) `computeLocalMatches()` — an instant, ungated, no-network substring match of the typed text against `ward_name` only, re-run synchronously on every keystroke starting from the first character, ranking wards whose name *starts with* the query above ones that merely contain it (alphabetical within each group) — this is what makes the dropdown appear immediately rather than waiting on a network round trip; and (2) `resolveLandmarkMatches()` — a still-debounced (400ms, `home-view.js`'s `debounce()`, 3-character minimum, since it's a real third-party network call) query against the public OSM Nominatim API (`https://nominatim.openstreetmap.org/search`, hardcoded `country=india`, `city=bangalore`, `format=jsonv2`, `limit=5`, `email=sss@gmail.com` — Nominatim's usage-policy-accepted identification method, since browsers won't let script set a custom `User-Agent` header — and the typed text as the dynamic `amenity` param) for resolving a typed **landmark** (a bus stop, locality, or other place that isn't itself a ward name) to the ward it physically sits in. Each Nominatim result is checked two ways before being shown: `findWardNameTextMatch()` fuzzy-matches (case-insensitive substring, checked in both directions, longest-`ward_name`-wins on a tie) the result's combined `name` + `display_name` text against every local `ward_name`; if that finds a candidate ward, the result's `lat`/`lon` is run through `wardAt()` (`maps.js`, the same point-in-polygon helper "Use my location" uses) and **must** resolve to that same candidate ward or the result is dropped entirely — a text match that geometry doesn't confirm (a coincidental name mention that isn't actually where the point is) is never shown, on either ward. When no ward name appears in the result's text at all, the point-in-polygon result is used directly with no text gate, unchanged from a plain "whichever ward contains this point" lookup — e.g. a landmark like "Vidhana Soudha" (no textual relation to any ward name) still resolves to and displays whatever ward its coordinates fall inside. A resolved ward is merged into the dropdown with a "near `<landmark>`" subtext (in place of the usual "Ward N · Corporation" line) filling any of the 6 rows the local match didn't already take, deduped by `uid`. A prior in-flight Nominatim request is aborted via a module-level `AbortController` before each new one fires, and a module-level `suggestRequestSeq` counter additionally guards every async landmark result against being applied after a newer keystroke has already superseded it (covers cases `AbortController` alone can't, e.g. the query dropping back below the 3-character minimum before an in-flight fetch settles). `#findList` itself is never filtered by any of this — it always shows the full ward list. Clicking a row navigates via the same `onOpenWard(uid)` callback the main ward list uses. The dropdown also closes on `Escape` and on any click outside `.find-search-wrap`. `data-loader.js`'s `nameIndex` is not used by any of this — it remains computed but unconsumed outside `data-loader.js`, as it was originally.
